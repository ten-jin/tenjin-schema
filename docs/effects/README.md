# Effect fields

[Back to tenjin-schema](../../README.md)

Effects can describe costs, selections, conditions, and instructions. Use the field definitions in [cardEffectTypes.ts](../../src/cardEffectTypes.ts) and the supported values in [cardEffectVocabulary.ts](../../src/cardEffectVocabulary.ts) when authoring more complex abilities.

The default vocabulary contains shared card/effect names. Consumers define specialized keywords, stats, phases, resource costs, and tags in their own vocabulary and pass it to `createCardEffectValidators` or `createConfigurationValidators`. The same vocabulary parameterizes the exported TypeScript types. The schema validates these names and their data structures; the consuming compiler maps printed rules to them, and the engine supplies their meaning.

```ts
import { cardEffectVocabulary } from 'tenjin-schema/cardEffectVocabulary'
import { createCardEffectValidators } from 'tenjin-schema/cardEffects'
import type { EffectInstance } from 'tenjin-schema/cardEffectTypes'

const vocabulary = {
  ...cardEffectVocabulary,
  CARD_STATS: [...cardEffectVocabulary.CARD_STATS, 'armor'],
  MODIFIER_TYPES: [...cardEffectVocabulary.MODIFIER_TYPES, 'fortified'],
  COST_TYPES: [...cardEffectVocabulary.COST_TYPES, 'fuel'],
  TURN_STEPS: [...cardEffectVocabulary.TURN_STEPS, 'dawn'],
} as const

const validators = createCardEffectValidators(vocabulary)
const effect: EffectInstance<typeof vocabulary> = {
  modifiers: [{ type: 'fortified', amount: { stat: 'armor', card: 'recipient' } }],
  costs: { phase: 'dawn', costs: [{ type: 'fuel', amount: 1 }] },
}
validators.isEffect(effect)
```

Cost containers can restrict payment to a configured current turn `phase`. Effect definitions use their own `phase` field for trigger or rule checks. Queries such as `targetQuery` and `eventSourceQuery` express eligibility through shared filters. Play permission `characteristic` and payment `playPermissionCharacteristics` fields carry opaque string tags interpreted by the consumer.

Temporary definitions use `duration` and `remainingUses`; `nextEnding` refers to the controller's next `ending` phase. `routing.resolvingPlayer: "eventController"` resolves for the player who performed the triggering action. `routing.resolvingPlayer: "eventPlayer"` resolves for the player the triggering event is about: its performer, or the turn player for phase events such as the start of a Beginning Phase. `routing.resolvingPlayer: "selectedOwner"` and `"selectedController"` resolve for the owner or the controller of the first card of the previous selection. `usagePerPlayer` tracks a separate once-per-turn allowance for each player. A replay with `exit: 'banished'` banishes the replayed card instead of putting it into the trash when it finishes resolving or leaves the board, like a play permission's banished exit; plays of that card from other sources exit normally. Ordered replay uses `flow.forEach` with `order: "chosen"`; owner-controlled play can offer `destinations: ["lastLocation", "base"]`. Token replacement uses `replacePlay` and spawn's `lastLocation` to retain the original destination. `value` carries the modifier's string-valued payload: type modifiers add card types and action-window modifiers add timing permissions; `effect.singleRecipient` keeps that effect's whole modifier bundle on one recipient at a time. These contracts describe the rules for consumers; schema validation does not implement their runtime execution.

`AbilitySet` contains the same behavior fields used on cards: ordinary `effects`, `activatableEffects`, `playModifiers`, costs, timing permissions, and limits. `CardEffectData` adds setup pools to that shared type. `grantAbilities` accepts an inline `AbilitySet` or a queried copy, with an optional `duration`. An inline grant uses the ordinary validators and compiler for its nested definitions and programs.

A copied grant uses `copyFrom: CardSetQuery`, optional `fields: (keyof AbilitySet)[]`, and optional `filter: { taps: boolean }`. Omitted `fields` copies the whole ability set; an empty list copies nothing. The filter matches definition metadata in `effects` and `activatableEffects`; it does not test whether the original card could currently activate the ability. An attached provider can query `affectingCard`, the attachment holder, to contribute a copy of the holder's abilities. Setup choices, card identity, stats, and types are outside `AbilitySet` and are not copied by this operation.

The outer definition evaluates provider conditions, recipient queries, and copy-source queries in the provider's context. Once granted, `self`, `here`, costs, selections, and stat expressions bind to the receiving card and its controller. Provider gates do not become conditions on the nested activation. An attached provider uses the holder as its affected card while retaining the attachment as `effectSource`. A passive grant follows its provider's active lifetime and recipient match, including attachment and site-control conditions. A resolved grant stays on the selected card instance until it leaves play or the specified duration expires; `duration: 'source'` also depends on the provider's current in-play lifetime. Expiring a grant prevents new activations/triggers; already queued effects and resolved modifiers retain their ordinary lifetimes.

Copied grants are live views: relevant card text, matching source cards, and their active grants are reevaluated as state changes. Copying retains each ability's original definition identity and its contributing grant path. An expansion must stop when that same contribution is encountered again on its path, preventing cycles between copied grants or an attachment copying its own contribution. Independent native definitions and grants from different providers remain independent. Costs, once-per-turn usage, and remaining uses belong to the receiving card's particular grant contribution; they do not share the original card's usage state. Full card transformations through `copySelection` remain separate. These are consumer execution rules; schema validation and compilation do not implement runtime grants.

Dynamic amounts use `{ payment: { cost: 'manaRecycle', group: 'additional' } }` to total committed payments of that cost in the named group. Omitting `group` totals that cost across the current payment context; canceled or speculative payments do not count. `{ count: 'previousSelection' }` counts a referenced card set, including captured selections on registered effects. It counts captured identities even after they move or die, rather than rerunning a board query. These expressions work wherever the contract accepts a dynamic amount.

`setupChoices` maps stable keys to pregame pools owned by the declaring player. Each pool has a catalog `query` and positive maximum `count`, with optional `distinctNames`, `excludeStarting`, and `ifInDeck` filters; the player may choose fewer than `count` definitions, including none, and selecting from a pool excludes definitions with an instance already on the board or chain; `excludeStarting` excludes names among starting cards and `ifInDeck` enables the pool when the player's deck has a matching definition. `{ from: 'setupChoice', key: 'additionalLeaders' }` references the entire chosen pool; an explicit `index` references one entry and is required for scalar use. These are card definitions, not mutable board instances. `createCards: { from: 'selection', to: 'leader', duration: 'source' }` creates distinct card instances from the selected definitions. Creation supports other configured zones and card types. Source duration tracks the creating source's in-play lifetime and removes only instances created by that application when the source leaves; existing starting leaders and other sources' creations remain independent. The consuming engine must implement these grants, amount expressions, setup pools, and creation lifetimes.

`infinityCost` describes an unbounded cost to choose and pay. Effect results read the committed quantity with a payment expression such as `{ payment: { cost: 'manaRecycle', group: 'additional' } }`. A labeled variable payment can be read independently of fixed costs of the same type. Variable resource payment declarations can allow zero explicitly. `drawMana.amount` accepts the same nonnegative literal counts and dynamic count expressions as other count consumers.

Subtraction uses an ordinary amount expression: `{ calculation: { operation: 'subtract', left: AmountExpression, right: AmountExpression, minimum?: number } }`. It returns left minus right, clamped to `minimum` when provided; omitting the clamp allows negative results. Operands may be literals, stat references, payment amounts, counts, aggregates, player stats, or nested subtraction expressions. Modifiers use this expression inside `amount`, as do damage, costs, and dynamic counts. Consumers evaluate all amounts in a resolved modifier bundle from the same state before applying that bundle, so a swap's second difference cannot read the first modification. Explicit effect sequences retain their normal timing and may see earlier changes. The consuming engine must implement payment references and shared subtraction evaluation; schema validation does not execute them.

`revealSelect` identifies matching cards publicly without moving, exhausting, or consuming them. Its amount and query use the ordinary selected-cost contract; board choices exclude facedown cards. An optional additional cost can offer two alternative queries (own hand or friendly board), selecting one card total. A successful choice is retained in that play's payment context as `{ from: "costSelection", cost: "revealSelect" }`; declining leaves that set empty. Ordinary amount conditions with query counts test whether the cost selected a card, and structured stat amounts read a specific selected card, such as `{ stat: "strength", card: { from: "costSelection", cost: "revealSelect", index: 0 } }`. Stat reads of cost-selected cards use their values as the cost was paid; later changes or zone changes do not affect them. `effect.reveal` continues to reveal cards during effect resolution. The engine must execute this information-only payment and retain its selection for the play's effects; schema validation alone does not provide execution.

Modifiers use `amount` for numeric payloads and `value: string` for string payloads. Each modifier contributes one value: `{ type: 'type', value: 'unit' }` adds a type, and `{ type: 'actionWindows', value: 'contesting' }` grants a timing permission. Granting several values uses several modifiers in the same effect. Type values include arbitrary tags; action-window values must come from the configured vocabulary. `replaceID` remains a replacement key and does not carry the type payload. Ability and activation `actionWindows` fields retain their existing timing meaning.

`singleRecipient: true` scopes replacement to the source card instance and effect identity. Choosing a different recipient with that effect removes the entire prior modifier bundle, then applies the bundle to the new recipient. Choosing the same recipient refreshes rather than stacks it; declining the optional choice leaves the old recipient unchanged. Other effects and other copies of the source keep their own modifier bundles. This policy does not change the modifiers' ordinary durations or remove unrelated modifiers from either card.

Shared site abilities use `activationPlayers: "turnPlayer"` to allow the current turn player to activate them regardless of site control; costs, choices, and resolution belong to that activating player. The default permission is `"controller"`. `modifierGrant` applies its modifiers to matching prospective plays before costs are calculated, carries a positive `uses` count, consumes one use at `consumeOn: "finalized"`, and expires at the end of the turn. `banishSelect` costs use their `query` to select and banish cards as payment, including cards in the activating player's discard. These contracts require execution support in the consuming engine.

Registered definitions accept `initiatingPlayer` as a normal player target or `{ ownerOf: EffectSingleCardReference }` / `{ controllerOf: EffectSingleCardReference }`. These references read the owner or current controller of the referenced card instance. `captureTargets: true` freezes referenced card identities from the registering resolution; it does not repeat the original selection when a later event occurs. In a registration, `previousSelection` addresses that captured set rather than the later event's subject. A registration with no duration persists independently of the originating card's board lifetime. `remainingUses` is consumed by matching events, even if the effect's requirements subsequently prevent an instruction.

Amount expressions support `{ count: { query: CardSetQuery } }` for current matching instances, `{ aggregate: { operation: 'min' | 'max' | 'sum', stat: CardStats, query: CardSetQuery } }` for their stat values, and `{ playerStat: { stat: PlayerStats, player: EffectPlayerReference } }` for a player's stat. The configured `PLAYER_STATS` vocabulary defaults to `points` and `xp`; other games can supply their own names. Empty queries yield count zero and empty aggregate sets yield zero for every operation. Expressions evaluate in the normal effect context when the amount is needed; passive and cost expressions recalculate as that context changes. References to preserved selections continue to count those captured identities, while query-based counts reevaluate their query. These expressions work in costs, cost multipliers, damage, modifiers, draw and XP counts, and selection or spawn counts. A cost multiplier scales the cost's amount. Consumers must implement these expressions and captured registrations; validation describes their contracts without executing them.

Activation discounts belong to the paying definition's `costs[].costReduction`. Each entry uses ordinary cost amounts, multipliers and `conditional` predicates; subtract each applicable reduction from the matching resource once, clamping the payable resource cost at zero unless an explicit cost floor applies. A negative reduction increases the cost. Counts and conditions evaluate in the activating player's payment context. A reduction can reference a declared `effect.select` target through `{ from: 'selection' }`: choose that target before calculating payment, capture any stat marked `previous: true` at that point, and retain the same identity for resolution. Do not execute effect instructions to obtain the discount. Normal `reduceCost` definitions with `costSource: 'cardPlay'` can likewise test the prospective play's declared target selection. Target validation, reductions and any additional choices precede committed payment; declining or canceling does not spend resources. Resolution retains the ordinary legality rules for those selected targets.

`control: { recalls: true }` combines the control change and subsequent recall in one instruction. If `readies: { action: 'exhaust' }` is included in the same effect, apply exhaustion before recall. Recall always goes to the recalled card's current player's base. The card's player determines the destination; the initiating or resolving player supplies event attribution, and recalling alone does not change control. Normal `moves: { type: 'recall' }` follows the same destination rule. These effects need no nested recall sequences or controller references in `routing.resolvingPlayer`.

A numeric modifier's `minimum` clamps the resulting stat after that modifier's adjustment; it does not clamp the adjustment amount or impose an unrelated permanent stat minimum. The field follows that modifier's normal duration and applicability. For example, `{ type: 'strength', amount: -4, minimum: 1, duration: 'turn' }` floors the resulting strength at one. Other numeric stat modifiers may use other numeric floors. `amount.calculation.minimum` remains separate: it clamps the computed amount before it is applied. These are consumer execution contracts; schema validation and compilation do not implement payment, control or stat evaluation.

`showdownStart` triggers on cards at a battlefield when a showdown begins there, whether or not that showdown starts a combat. It fires once per showdown, before that showdown's first priority, and does not fire for cards that arrive after it began. Consumers must emit this event; validation does not.

`channelAddition` is a resource-draw replacement carried by its source card. While that modifier applies, whenever the source's controller would draw one or more cards from their resource deck, they draw that many plus `amount` (default one) instead; the additional cards enter exhausted, and several sources add their amounts. A draw of zero is not replaced. Completion of the original instruction depends only on its requested count. Consumers must implement this replacement; validation does not execute it.

`CardConditional.compare.value` uses `AmountExpression`, including ordinary `{ count: { query } }` expressions. The condition's left amount operand and the comparison's count query evaluate independently in the same condition context. Explicit controller filters remain local to their queries. Comparisons retain their operators and use the same expression evaluation rules as costs, modifiers and damage.

Movement costs use the ordinary per-cost `multiplier`. While evaluating a `moveCost` rule, `selection` addresses the proposed simultaneous movement batch to the destination governed by that rule. It contains moving card identities, not cards already at that destination; the query may filter those identities by type or controller. Evaluate the whole batch before committing payment or moving any of it, and apply each matching movement-cost rule once to the batch. For example, a movement cost can use the multiplier `{ calculation: { operation: 'subtract', left: { count: { query: { source: { cards: 'selection' }, cardTypes: ['unit'], players: 'all' } } }, right: 1, minimum: 0 } }`. Zero or one unit gives a zero multiplier; three units give two. Separate movement batches calculate separately. The activating/moving player pays these costs, while the provider's ordinary source and target conditions determine whether the rule applies.

`damage.distribution: 'split'` makes `damage.amount` a single damage budget shared among the selected recipients. Evaluate that budget once and choose allocations when the associated selection is made; preserve target identity and allocation through resolution. Selection bounds still govern the recipient set. Allocations are integer damage quantities, with at least one assigned to every chosen recipient, and total the budget when recipients are chosen. With an empty recipient set allowed by the selection, no damage is applied. Apply all remaining legal recipients' allocations simultaneously; a recipient becoming illegal does not redistribute its allocation. Without `distribution`, damage retains its usual per-recipient amount. `reciprocal: true` remains the existing simultaneous exchange between two units. These contracts describe consumer behavior; validation does not execute movement payments or damage allocation.

`draw`, `gainXP`, `drawMana.amount` and `spawn.count` share the ordinary count expressions, including `{ count: { query } }`, captured-reference counts, payments, stats, aggregates and arithmetic. Literal counts are nonnegative safe integers; a resolved dynamic count must satisfy the same bounds. Evaluate each count once at that instruction's normal resolution point in its effect context, and apply it only to that instruction. A zero count draws no cards, grants no XP or creates no tokens. Query counts reevaluate their query at that point; a reference count retains captured identities. Spawning records only the instances it created as the subsequent `previousSelection`, including an empty set when nothing spawns. The consuming engine must implement these instruction counts and preserve existing sequencing; validation does not execute them.

Normal `play` instructions use an optional `payment` policy. `true` pays the card's normal cost; `false` or omission waives its normal cost; `{ waive: ['mana'] }` waives only the configured `mana` cost. `waive` accepts configured cost types. `{ costReduction: [{ type: 'mana', amount: 5 }] }` pays the normal cost with a reduction to that resource; reductions reuse `EffectCost` amounts, multipliers, conditions and floors, with the same subtract-once and zero-clamp rules as activation reductions. The policy applies to the normal cost group; mandatory additional costs, optional additional choices and the cost of the ability causing the play retain their ordinary rules. Evaluate the policy in the paying player's context before committing payment, retaining previous selections and any captured `previous: true` stat values. `controller`, destinations and play legality remain independent of payment. Replay retains its explicit replacement `costs`; copying retains its existing separate mode. Consumers must implement these policies; the schema does not execute payment.

`{ count: { query, distinctTypes: ['bird', 'cat', 'dog', 'fox'] } }` counts how many distinct listed type values are represented among the query's matching cards. Match the query first, then examine those cards' effective types, including granted types. Count each listed value at most once: several Birds contribute one, one Bird/Dog contributes two, and unlisted types contribute nothing. Repeated listed values do not increase the result. An empty query result or empty `distinctTypes` list yields zero. Omitting `distinctTypes` retains ordinary instance counting. This expression is shared by amounts, discounts and comparisons; it does not change which cards a query returns. A card-set requirement may use `{ count: CountExpression, min?: number, max?: number }` instead of `query` to bound an explicit count, with the existing default minimum of one. Other tags, types and count expressions use the same contracts. Consumers must evaluate these counts and requirements.

`{ calculation: { operation: 'add' | 'subtract' | 'multiply', left: AmountExpression, right: AmountExpression, minimum?: number } }` composes ordinary amounts recursively. Evaluate both operands in the same context when the consuming instruction needs the amount, apply the operation, then clamp the result to `minimum` if present. Operands can use configured core or damage amount references as well as counts, payments, stats and other calculations. A dynamic instruction count must still resolve to a nonnegative safe integer. Arithmetic scales only its consuming amount, so a damage calculation cannot multiply a sibling draw, XP award or replay cost. Modifier amounts reevaluate in their ordinary passive context; their separate `minimum` still floors the resulting stat.

`{ count: { event: HistoryEvent, card: EffectSingleCardReference, role: 'source' | 'subject', window: 'turn' } }` counts recorded occurrences of a configured event involving that physical card instance in the current turn, before the consuming instruction executes. `subject` matches the card the event happened to; `source` matches the card that caused it. Multiple matching occurrences count separately. Count all occurrences since the start of the current turn, including another player's turn, independently of the card's current zone or controller. An absent card or no matching events yields zero; a different instance of the same card definition does not share the history. This expression is available to every ordinary amount consumer and can be nested in arithmetic. Event names come from each game's `HISTORY_EVENTS`, configured independently of triggered ability keys in `EFFECT_KEYS`; rule checks that emit no event do not create occurrences. Engines must record the relevant events even when no triggered ability listens to them.

For `damaged`, record one occurrence for each recipient that actually receives positive damage, with that recipient as subject and its damage-dealing card as source. Damage points are not event counts; fully prevented, zero or disallowed damage creates no occurrence. Simultaneous recipients each contribute one after the damage amount has been evaluated, so the current instruction cannot count its own damage toward itself. The consuming engine must implement arithmetic and event-history evaluation; schema validation and compilation do not execute them.

Numeric conditions use `{ type: 'amount', amount: AmountExpression, min?: AmountExpression, max?: AmountExpression, compare?: CardConditionalCompare | CardConditionalCompare[], not?: boolean }`. `amount` is required and follows ordinary amount evaluation; it is not a modifier adjustment. Evaluate that left operand and every bound in the same condition context. Minimum and maximum are inclusive; a missing comparison operator means equality, and a comparison list requires every comparison to pass. With no bounds or comparisons, test that the operand is nonzero. Apply `not` to the complete result. Existing predicates retain their implicit operands. Games opt into the generic predicate by including `amount` in `CONDITIONAL_TYPES`, and all nested stats and events still use that game's configured vocabulary.

In `conditionalsSource`, `recipient` denotes the source card being checked; in `conditionalsTarget` and a card query, it denotes the target/candidate being checked. The effect's `affectingCard` continues to denote the provider or receiving card whose ability is being evaluated. Thus the same subject-role event count handles both source and target conditions without moving gates into effect resolution. A movement event is recorded before its trigger conditions are checked, so first/second/third-move predicates see counts of one/two/three. Failed or same-location movement creates no occurrence; each successfully moved card, including each member of a swap, records its own occurrence. The optional event-count flag `currentObject: true` restricts the history to the referenced card’s current game object, intersected with the current turn. Record the object identity associated with the event role being counted. The consuming engine defines when a card receives a new game-object identity. Omitting the flag keeps physical-instance history across object changes. A combat-ended condition can count earlier damage received by its own source card. Event-count amounts used to calculate new damage still exclude that damage instruction's future occurrences.

Selection-total bounds use a sum aggregate over `{ players: 'all', includeSource: true, source: { cards: ['selection', 'recipient'] } }`. While testing a candidate, `selection` contains the chosen batch and `recipient` is the candidate; the union deduplicates identities so an already chosen candidate never contributes twice. Include the provider if it belongs to that batch. Recheck the complete batch before committing the selection, with `recipient` bound to a chosen member or absent for an empty batch, rather than falling back to the provider. Empty batches sum to zero and are allowed when the selection's minimum and amount bounds allow them. Do not treat a selection-dependent aggregate as an independent per-card filter; partial-selection pruning must not eliminate a batch that can still meet a minimum or another comparison when complete.

Board-wide and location totals specify their query inside the aggregate rather than borrowing the surrounding query implicitly. Use `exclude: 'affectingCard'` to exclude the provider, or `source.location.card: 'recipient'` to anchor a location query to the checked card. Conditions remain checked at their existing trigger, payment, selection or passive-rule evaluation point. Consumer execution must support these generic conditions and contexts; schema validation does not implement them.

Cost adjustments use the individual cost's `amount` or per-cost `multiplier`, with adjustment conditions in `costReduction` entries. The signed amount, matching domains, resource kind, conditions and payment group retain their existing meaning. No count can scale other entries or effect instructions through an enclosing cost container.

Numeric card-stat predicates use `{ type: 'amount', amount: { stat: 'strength', card: 'recipient' }, min: 5 }` and the same form for `attack`, `mana`, `manaRecycle` and `damage`. The `mana` and `manaRecycle` stat operands read the checked card's cost components. `damage` reads currently marked damage; a boundless condition tests nonzero marked damage, independently of damage-event history. Points and XP conditions read `{ playerStat: { stat: 'xp', player: { controllerOf: 'recipient' } } }` (or `points`) so source and candidate conditions follow the checked card's controller, including prospective controller context.

Stat operands in conditions retain the existing evaluation context: use projected marked damage and XP, and supplied provisional strength/attack values during stat calculation. When evaluating a stat's own conditional modifiers, use the calculation's current input value rather than recursively recalculating that stat. Captured comparison operands marked `previous: true` retain their original selection-time values. Preserve all bounds, comparison operators, negation and payment guards: `unlessPaidAdditionalCost: true` bypasses the entire condition when that additional cost was paid. These evaluation contracts require consuming-engine support; the schema only validates their representation.

Query counts accept an optional scalar `card` reference: `{ count: { query, card: 'recipient' } }`. Resolve that reference in the surrounding amount context first, then evaluate the query's relative player filters (`self`, `team`, `opponent`), locations (`here`) and `includeSource` against that card and its projected controller. Keep provider references, captured selections and payment context intact. The anchor applies only to this count's query, not sibling amounts or comparisons. An unresolved explicit anchor yields zero rather than falling back to the provider. Omitting `card` preserves normal effect-context query evaluation. This also works with `distinctTypes` and in all other amount consumers.

Count predicates use `{ type: 'amount', amount: { count: { query, card: 'recipient' } }, min: 1 }` with ordinary bounds and comparisons. Use `exclude: 'recipient'` to exclude the checked card explicitly; queries with `includeSource: true` retain inclusion unless explicitly excluded. A query count does not implicitly exclude its anchor. Source gates bind `recipient` to their source, target gates to their target, attached modifiers to their holder, and site-query predicates to the candidate site. Count comparisons retain the independent context of each operand: rebinding the left query does not rebind the right. Nested candidate predicates receive their own checked card, without changing the outer count anchor. Consumer execution must implement the explicit query anchor and retain these bindings.

To add one to a captured stat value, use `{ calculation: { operation: 'add', left: { stat: 'strength', card: { from: 'previousSelection' }, previous: true }, right: 1 } }`. The left operand keeps the same captured card and stat lifetime; the calculation does not recapture it or read its current strength. It uses the existing arithmetic contract, including unresolved-operand handling.

`GAME_STATS` configures game-wide numeric values independently of `PLAYER_STATS` and `CARD_STATS`. Its default vocabulary contains `roundNumber`. Read one through `{ gameStat: { stat: 'roundNumber' } }`; other games may configure names such as `turnNumber` or `cycles`. A game stat has no card or player scope, and it works in every shared amount position, including arithmetic, counts, bounds and comparisons. Read the game's current stored value at the enclosing instruction or condition's normal evaluation point.

Instruction repetition, copies, ready budgets and pre-reveal scry counts use `CountExpression`: `flow.repeat`, `triggerRepeat.amount`, `play.copies`, `readies.amount` and `preScry`. Literal and resolved counts must be nonnegative safe integers; zero is meaningful and must not be replaced with a default. Existing omitted-field defaults stay unchanged. Resolve `flow.repeat` once on entry to the repeated flow and retain that total number of executions; do not reread a changing query after each iteration. The repeated body's amounts still evaluate at their ordinary instruction boundaries. Resolve each applicable `triggerRepeat.amount` when collecting the trigger's repetitions, retaining the existing eligibility gates and adding that many extra executions to the original trigger. Do not introduce new payment or usage checks merely to evaluate a repeat amount.

Resolve `play.copies` once before creating copies of its existing subject; zero creates none. Resolve `readies.amount` once as the budget for the eligible batch of cards for `ready`, `exhaust` or `toggle`; zero changes none, and omission retains the existing unrestricted budget. Evaluate `preScry` at the existing pre-reveal scry boundary, retaining the deck, resolving player and order relative to revealing. Counts preserve selection identities, subject routing, costs and event attribution. Resolved negative, fractional or unsafe counts are invalid and must not be silently rounded or treated as an unrestricted budget.

`addBuff` and `addPoints` accept signed `AmountExpression`, including negative literals and unclamped subtraction. Evaluate adjustments in the existing instruction context, with `recipient` referring to each affected card for `addBuff` adjustments and player references retaining ordinary routing for point adjustments. The consuming engine applies signed adjustments according to the configured stat and scoring rules. Zero makes no adjustment. These are adjustments rather than replacement totals. Existing finite literal values remain valid. The schema validates expression structure without executing it; consumers evaluate these dynamic fields.

Player stats can read turn-scoped values through `{ playerStat: { stat: PlayerTurnStats, player: EffectPlayerReference, window: 'turn' } }`. `PLAYER_TURN_STATS` is configured independently of `PLAYER_STATS`; the existing form without `window` still reads current player state such as points and XP. Both forms compose with arithmetic, comparisons, costs and instruction counts. The turn window is the current game turn, including another player's turn, and resets at the same boundary as the existing player turn state. Missing totals yield zero. Resolve explicit players and captured controller/owner references using the ordinary effect context and projected controller/stat values; do not infer a player from the turn owner.

Numeric turn predicates use ordinary `type: 'amount'` conditions with turn-scoped player-stat operands. Use `player: { controllerOf: 'recipient' }` to read the checked card's controller: the source in source conditions, or the target in target conditions. Cost `multiplier` also accepts `AmountExpression`, including these operands.

Filtered history amounts use the same count expression as physical-card event counts, with an `EventQuery` in place of `card` and `role`. Simple conditions use the compact `eventCount` form described below. Their captured types, controller/team, phases, paid costs and locations retain their existing meanings. Schema validation does not execute turn-stat or history reads; consumers evaluate these reads.

`{ count: { event: HistoryEvent, query: EventQuery, window: 'turn' } }` counts recorded occurrences matching a player and captured metadata. `HISTORY_EVENTS` defines recordable names, independently of the ability trigger vocabulary; defaults include the existing event names plus `activation`. Query counts and physical-card event counts share these names and compose with all ordinary amounts. A rule check creates no occurrence simply because its name is configured. Record relevant events even if no triggered ability listens to them. Each matching occurrence contributes one; repeated occurrences involving the same physical card remain separate, and overlapping type matches do not multiply one occurrence. No matching events or an unresolved anchor yields zero. Query counts do not accept the scalar count's `card`, `role` or `currentObject` fields.

An event query accepts optional `player: EffectPlayerReference` and `role: 'actor' | 'subjectController'`. `actor` matches the player responsible for the recorded occurrence, such as the player who initiated a play or activation; `subjectController` matches the subject's recorded controller, as death histories require. `relation: PlayerTarget` defaults to self and expands from the referenced player to its team, opponents or all players using the game's configured relationship rules. Evaluate the reference and relationship in the consuming context, but match the recorded event player/controller; later control changes do not rewrite history. Deduplicate matching player sets, not event occurrences. `phase` filters the recorded event phase, independently of the checked card's latest event or phase. The turn window retains the current game-turn reset boundary, including another player's turn.

`subject` filters captured subject metadata: `cardTypes` matches any outer alternative, nested arrays require every listed type, and `excludeCardTypes` rejects any listed value. Arbitrary tags follow the same rules as other type queries. An empty outer type list matches none; inner arrays must be nonempty and cannot contain further arrays. Empty excluded lists add no restriction. `exclude: EffectCardReference` excludes matching physical subject identities across all their recorded occurrences, independently of zone/object resets. `isAtSite` tests the recorded destination/location for the occurrence, rather than today's location. Omitted fields impose no restriction. The explicit `typesFrom: 'current'` option changes only type filtering to the referenced physical subject's current types; missing subjects cannot match a live type filter. It does not change recorded player, phase, costs or location. Event subject filters are not `CardSetQuery` and never perform a new zone query or implicit source exclusion.

Occurrences are completed by default. `stage: 'initiated'` includes pending and completed attempts from the same ledger, counting each attempt once rather than once per stage. Consumers retain one occurrence per attempt and update its completion state on resolution. Use explicit subject exclusions and `typesFrom: 'current'` when a query needs them. Recorded activation metadata is supplied by the consuming engine.

`paidCosts: EffectCostContainer` filters each occurrence's captured payments: all required cost thresholds must be satisfied by that same record, summing matching payment types within it. Do not combine payments from separate plays or substitute printed costs, discounts or waived amounts. Evaluate dynamic thresholds in the ordinary consuming context, retaining captured references and the existing paid-cost threshold behavior. Location filters use the captured destination recorded with the occurrence.

Death queries use `event: 'killed'`, `role: 'subjectController'`, and captured types, controller and turn step. Global death gates use `relation: 'all'`; enemy gates use `opponent`; friendly-unit gates use `team` plus `cardTypes: ['unit']`. Preserve the occurrence's pre-zone-change/controller metadata. Placing `phase: 'beginning'` inside the query filters the recorded occurrence's phase. The schema validates the query's structure; consumers supply event recording and evaluation.

Condition payloads contain their operand (`amount` for numeric conditions), bounds/comparisons, inversion, payment bypass and the existing checked-card `eventPhase` gate. For history amounts, put card-type and paid-cost filters in an event query's `subject` and `paidCosts`. For compact `eventCount` conditions those filters are direct fields. Put current card queries inside `{ count: { query } }` or an aggregate operand. The strict object schema enforces this shape. Captured occurrence phases belong in `count.event`'s `query.phase`; `eventPhase` retains its separate checked-card meaning. Existing exported predicates and remaining choice/state conditions retain their behavior.

`CARD_RELATION_TYPES` configures the keys of `CardSetQuery.relations`, alongside the other game vocabularies. `CardRelationType<V>` and nested relation validation use that same vocabulary. Each key accepts one requirement or an array of requirements; their queries and count expressions retain the enclosing game's vocabulary. The default relation names and their semantics remain unchanged. Games define how their configured relations are evaluated.

History `EventQuery.player` defaults to `{ controllerOf: 'recipient' }`, and `role` defaults to `actor`. Defaults are independent: an explicit `subjectController` still uses the checked card's controller unless `player` is supplied. `relation` retains its existing `self` default. Explicit player references such as `self` or `{ ownerOf: 'eventSubject' }` override attribution and retain their distinct meaning. An empty query counts completed events by that controller in the requested window. `stage: 'initiated'`, subject filters and exclusions remain explicit. Consumers must apply these query defaults when evaluating counts.

`eventCount` is a compact generic history condition. For example, `{ type: 'eventCount', event: 'played', stage: 'initiated', exclude: 'recipient' }` tests initiated plays by the checked card's controller, excluding that card. It accepts any configured `HISTORY_EVENTS` name and shares ordinary conditions' `min`, `max`, `compare`, `not`, `unlessPaidAdditionalCost` and `eventPhase`. With no bounds/comparison, it requires a nonzero count (at least one occurrence); explicit `max: 0` checks absence. `window` defaults to `turn`, `player` to `{ controllerOf: 'recipient' }`, `role` to `actor`, and `relation` to `self`. Stage defaults to completed occurrences; it must not default to initiated plays.

The compact form has exactly the same history operand as `{ type: 'amount', amount: { count: { event, window: 'turn', query } } }`. To reuse the history-count evaluator, place `cardTypes`, `excludeCardTypes`, `exclude`, `typesFrom` and `isAtSite` in `query.subject`; place `player`, `role`, `relation`, `phase`, `stage` and `paidCosts` directly in `query`. Apply the ordinary condition bounds and inversion to that count. Captured `phase` still filters recorded occurrences, while `eventPhase` checks the recipient's phase. The compact form never performs a current-zone query or excludes its source implicitly. Payment thresholds remain on one occurrence and subject exclusions retain physical-card identity. Consumers evaluate this condition.

Count expressions remain available for arithmetic, dynamic instruction amounts and physical-card event counts (`card`, `role: 'source' | 'subject'`, and `currentObject`). Compact conditions accept filtered occurrence metadata and do not mix in those physical-card count fields. Both forms reuse the same event vocabulary and metadata validators; games opt into `eventCount` through `CONDITIONAL_TYPES` independently of their trigger vocabulary.

Compound conditions use `{ type: 'all' | 'any', conditional: [...] }`. `all` requires every child; `any` requires at least one. Empty `all` is true and empty `any` is false. A group's `not` inverts the complete aggregate result, so `{ type: 'all', conditional: [A, B], not: true }` means "not both A and B." Groups accept the ordinary payment bypass and checked-card `eventPhase` guards, but no numeric operand, bounds or comparisons. Games opt into each group type through `CONDITIONAL_TYPES`; children use the same game vocabulary recursively.

Each child evaluates its complete condition, including its own inversion and guards, in the parent's unchanged checked-card, captured-reference, player and payment context. Aggregation does not select a new card or change the anchor. Apply group inversion after aggregating the child results, then apply the group's ordinary guards. Existing condition arrays remain conjunctions; use groups only when the nesting carries a different meaning. Consumers evaluate these groups.

Effect-mode choices share selection bounds: `count` is the maximum number of options chosen (default one), and `min` is the minimum (default the full count). `{ count: 2, min: 0, distinct: true }` permits up to two different options; `{ count: 3, min: 2, distinct: true }` requires two or three different options. A fixed count keeps its existing representation without `min`. These bounds apply to player choices; revealed-card matching choices retain their automatic matching contract. Consumers must implement minimum-choice handling; schema validation does not execute choices.

An external provider may supply an additional payment through an `onCosts` definition with `costSource: 'cardPlay'`, a prospective-card `targetQuery`, and an ordinary `effect.costs` container. `optionality: 'optional'` offers the complete payment group; its `costReduction` applies to the normal card-play payment only if that group is paid. Provider costs use explicit selected-card queries such as `{ source: { cards: 'effectSource' } }`, so paying the provider never changes to paying the prospective card. Validate and reserve the complete payment before applying its reduction; declining or canceling supplies no discount and spends nothing. Provider eligibility and incoming-card filters retain the ordinary definition contexts. Consumers implement these payment groups and reductions.

Type filters use `CardTypeFilter`: `cardTypes: ['unit', 'gear']` means unit OR gear; `cardTypes: [['unit', 'bird'], 'gear']` means (unit AND bird) OR gear. Queries, captured history subject filters, compact event-count conditions and play destinations use this same shape. `cardTypeFilters` exports matching, type discovery and intersection helpers; consumers must evaluate nested groups together rather than flattening them for matching.

`EffectConditions.phase` checks the current turn phase independently of a card's recorded `eventPhase`. A normal modal `choice.usage: "oncePerTurn"` limits each option separately; it does not limit the enclosing trigger to one activation. Track that history by provider, choice and option. A bounded `modifierGrant` may also carry `playTo` permissions and an `onPlayed` continuation. Apply permission before destination selection (including facedown plays), commit the continuation to the same matching finalized play, and consume one use only on finalization. Cancelled plays and payment attempts consume no use; unused grants expire at turn end. `zoneChanges` to `hand` with `event: "draw"` draw the specified cards, preserving normal draw events rather than treating them as returns. A sourced inspected draw resolves before recycling the remaining inspected cards to their owners. These serialized contracts require corresponding consuming-engine support.
